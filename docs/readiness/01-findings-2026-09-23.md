## 1. The official standard, verbatim from the PDF

Desired Output: reconstruction type 3D Mesh / Point Cloud; processing time < 15
minutes for a 10-minute video; spatial accuracy ≤ 1 m; coverage entire visible scene;
output formats OBJ, PLY, LAS, GeoTIFF, .glb/.gltf, .fbx; visualisation web or desktop.

Evaluation weights: accuracy 30, completeness 20, speed 20, innovation 15,
scalability 10, UI 5. Mandatory inputs: drone video 1080p/4K, GPS coordinates, flight
metadata. Optional: IMU, barometric altitude, camera intrinsics, RTK/PPK.
Dataset: "Will be provided real time."

The PDF gives weights, not a scoring formula. No pass/fail threshold is derived from
them anywhere in this project.

## 2. Two arithmetic defects in the benchmark evidence - corrected

Both were in analysis scripts under `scratch/`, not in the run path. The reported
figures were wrong; the underlying runs were not re-executed (GPU-gated), so the
corrections below were recomputed from the saved pose files.

### 2.1 Umeyama scale inflated 3x, so every error quoted against it was inflated

`scratch/gpu_bench.py` divided the SVD trace by `mean(xs**2)` - the mean of the
squared *components* - instead of `mean(|xs|**2)`, the mean squared *vector norm*.
That inflates the fitted scale by the dimension, 3.

Recomputed from `scratch/gpubench/room_w_jsonl/keyframes_poses.jsonl` and
`pose_priors.jsonl`, same 172-fit / 115-holdout split:

| Figure | As saved | Corrected arithmetic |
|---|---:|---:|
| Fitted scale, m/unit | 0.834933 | 0.278311 |
| Hold-out RMSE | 2.7646 m | **1.1389 m** |
| Hold-out median | 2.6935 m | 0.9129 m |
| Hold-out P95 | 3.6164 m | 1.7427 m |
| Hold-out max | 3.8754 m | 1.9354 m |

What this does and does not mean: the corrected hold-out RMSE is 1.14 m against a
**phone VIO/AR trajectory that drifts by construction**, not against surveyed
checkpoints. It neither meets nor fails the ≤ 1 m target; it is the wrong reference
to judge that target with. The saved file `scratch/gpubench/scale_validation.json`
still holds the uncorrected figures and is now superseded by this table.

### 2.2 View support counted each COLMAP track token as a view

`scratch/gpu_ablation.py` used `len(fields) - 8`; a track entry is a *pair* of tokens
(IMAGE_ID, POINT2D_IDX), so the count was double. Actual mean support:

| Model | Reported | Actual |
|---|---:|---:|
| room_w_jsonl exhaustive | 12.017 | **6.009** |
| room_seq sequential | 9.621 | **4.810** |

### 2.3 A third defect, in the format writer rather than the analysis

`survey_formats._epsg_from_wkt` returned the **first** EPSG authority in a WKT string.
In a full PROJCS that is the spheroid's 7030, so every GeoTIFF written from a real
UTM definition would have carried `ProjectedCSTypeGeoKey = 7030` - an ellipsoid
labelled as a projected CRS. Fixed to take the CRS's own (last) authority, with a
regression test in `tests/test_survey_formats.py`.

## 5. Honest list of what is still unproven

1. Metric accuracy ≤ 1 m against independent surveyed checkpoints.
2. Coverage of the entire visible scene against an independent reference surface.
3. < 15 minutes end to end on a 10-minute 1080p single-pass clip, on declared hardware.
4. Any output validated by a third-party reader (no GDAL/laspy/PDAL is installed; the
   project's own readers re-parse what its writers produce, which is self-consistency).
5. Textured mesh: Poisson gives per-vertex colour, not a UV texture. The export
   manifest states `claims_textured_mesh: false`.
6. Reconstruction of occluded surfaces: measured, weak and unobserved are kept
   separate and nothing is inferred into a measured product. This is a deliberate
   limit, not a gap to close by guessing.
7. One-click operation: the survey reconstruction is still launched from the CLI
   behind an explicit GPU approval flag, not from the dashboard's Run lane.

## 6. Real-data proof, run later the same day

GPU was approved for this session, so the new delivery path was executed against a
**real** reconstruction instead of a fixture: `scratch/gpubench/room_w_jsonl`, the
1,568,438-point fused cloud measured on 23 September. Harness:
`scratch/real_delivery_proof.py`, output `scratch/real_delivery/`.

**What the clip actually is:** a 139 s handheld phone video at 960x720 with an ARCore
VIO track. There is no drone GPS for it, so the VIO camera track was fed in as the
position source and the origin latitude/longitude is a declared stand-in. That makes
this a proof of the **machinery**, not a georeferencing acceptance run, and the
summary file carries `not_a_gps_acceptance_run: true`.

| Result | Value |
|---|---|
| Cameras matched / inliers | 287 / 287 |
| Alignment scale | 0.27876 m/unit |
| Alignment fit RMSE | 0.637 m (a fit residual, not accuracy) |
| Formats delivered, local ENU set | 4 of 6 (PLY, LAS, glTF, FBX) |
| Formats delivered, georeferenced set | **5 of 6** (PLY 23 MB, LAS 53 MB, GeoTIFF DSM, glTF + 25 MB bin, FBX 67 MB) plus a 7 MB WGS84 position table |
| CRS derived | EPSG:32643, WGS 84 / UTM zone 43N, from the declared origin |
| Region observability | 8 of 8 cells observable at 2 m; `not_measured` caveats carried through |
| Throughput prediction | 3960.1 s predicted for 287 frames at 1000 px |

Three findings worth keeping:

1. **The prediction model validates against the measurement.** It predicted 3960.1 s;
   the real stitched run took 4001.4 s - 1.0% error. The model is usable for
   "will this finish in time" planning, and it still says `fits_deadline: false`,
   which is the honest answer for this budget on this card.
2. **The corrected Umeyama scale is independently confirmed.** §2.1 recomputed the
   fitted scale as 0.278311; `survey_georef`'s own RANSAC Sim(3) fit on the same
   cameras gives 0.278760. Two different estimators agreeing to 0.2% is the check
   that the correction, not just the arithmetic, was right.
3. **A real bug in the new code, found only by running it.** `mesh_command` passed the
   dense *directory* to `poisson_mesher`; COLMAP 4.1 takes the fused PLY path and
   fails with `does not match file extension .ply`. So OBJ came back `not_delivered`
   on real data even though the synthetic test passed. Fixed, with a regression test.
   The lesson is recorded in `02-wiring-ledger.md`: the fake-subprocess test style
   proves the plan, never that the external tool accepts it.
